# AGENTS.md — правила работы AI-агента

Проект: библиотека — бронирование книг и очередь читателей.
Стек: React 18 + Vite, Django 5 + DRF, SQLite 3, JWT (SimpleJWT).
Требования — `docs/SPEC.md`, задачи — `docs/PLAN.md`.

Этот файл — главный источник правил. Если агент повторяет ошибку — добавь правило
сюда и зафиксируй в `docs/AI_LOG.md` (минимум 3 реальных изменения за проект).

## 1. Язык и стиль

- Код, имена, комментарии — **английский**. Документация и тексты UI — **русский**.
- Простые решения: без метаклассов, сигналов, кастомных менеджеров и декораторов
  ради декораторов.
- Функция/метод — до ~40 строк, одна ответственность.
- Магические строки и числа — в константы (`loans/statuses.py`).
- Комментарий объясняет **почему**, а не что.

## 2. Границы слоёв

```
backend/config/        настройки, роутинг
backend/users/         User, роли, JWT, activity_log
backend/catalog/       Book, BookCopy, доступность
backend/loans/         Loan, статусы, защита от пересечений
backend/reservations/  очередь, удержание
backend/reports/       агрегаты и CSV
frontend/src/api/      axios + refresh-интерцептор
frontend/src/auth/     AuthContext, ProtectedRoute
frontend/src/pages/    экраны
```

- Бизнес-логика — только backend. Frontend не решает, свободен ли экземпляр.
- Расчёт `due_date`, проверка пересечений, матрица статусов, выдача удержания —
  в backend.
- Сериализаторы только валидируют формат.
- Логика бронирования — в `loans/services.py`, очередь — в
  `reservations/services.py`, не во вьюхах.

## 3. Обязательные инварианты

### 3.1 Защита от двойной выдачи
- Создание брони **всегда** внутри `transaction.atomic()`.
- Транзакция обязана брать блокировку записи до чтения: в настройках
  `"transaction_mode": "IMMEDIATE"`. На SQLite это единственная защита от гонки,
  потому что блокировок строк нет и `select_for_update()` ничего не блокирует.
- Только после начала транзакции — проверка пересечения и `INSERT`.
- Запрещено: обычный `SELECT` до начала транзакции, проверка без транзакции,
  запросы вне соединения транзакции, `transaction_mode: "DEFERRED"`.
- Учитывать только брони в статусах `created` и `active` и действующие
  удержания других читателей.
- Пересечение: `start_date < new_due AND due_date > new_start`.
- Конфликт → `409` с `code: "copy_taken"`, нет экземпляров → `409 no_copies`.
- Удалять или ослаблять `transaction_mode: "IMMEDIATE"`, проверку пересечений и
  тест на 10 потоков **запрещено**. Тестовая база — файл (`TEST.NAME`), иначе
  потоки получают `database table is locked` на in-memory базе.

### 3.2 Очередь и удержание (особое правило)
- Порядок строго FIFO: `ORDER BY created_at, id`.
- Одна активная заявка читателя на книгу. Повтор → `409 already_queued`.
- Возврат (`active → returned`) и выдача удержания — **одна транзакция**:
  блокировка записи (`BEGIN IMMEDIATE`) → освободить экземпляр → первый
  `waiting` получает `ready`, `hold_until = now + 48 часов`.
- Пока удержание действует, экземпляр недоступен другим.
- Просроченное удержание (`hold_until < now`) считается недействительным без
  фоновых задач: при проверке доступности и при следующем возврате заявка
  становится `expired`, экземпляр уходит следующему.
- Заявка `ready` → `fulfilled` в момент создания брони этим читателем.
- Если читатель с удержанием оформил бронь на **другой** экземпляр, удержанный
  экземпляр сразу передаётся следующему в очереди, а не ждёт 48 часов.

### 3.3 Права доступа
- Роль берётся из проверенного JWT; `user_id` — никогда из тела или URL.
- Queryset всегда фильтруется: reader → `reader=request.user`, librarian/admin →
  всё, что разрешено ролью.
- Чужой объект → `404`.
- Скрытие кнопки в React — не защита.
- Новый эндпоинт без теста на права не готов.

### 3.4 Статусы
- Матрица только в `loans/statuses.py`:
  `created → active, cancelled`, `active → returned`, конечные — без переходов.
- Недопустимый переход → `409 bad_transition`.
- Смена статуса + `LoanStatusHistory` + `ActivityLog` — одна транзакция.
- Читатель может только отменить свою бронь в статусе `created`.

### 3.5 Секреты
- `SECRET_KEY` и `DEBUG` — только из `.env`. База SQLite пароля не требует.
- В репозитории только `.env.example`.
- Не печатать значения из `.env` в чат, команды и вывод. Если секрет попал в
  `docs/prompts/`, его меняют (`SECRET_KEY`), а историю не редактируют.
- В JWT не класть лишние данные: payload читается кем угодно.

## 4. База данных

- SQLite 3: один файл `backend/db.sqlite3`, отдельный сервер не нужен. Кодировка
  UTF-8, режим `transaction_mode="IMMEDIATE"` обязателен (см. 3.1).
- SQLite не поддерживает блокировки строк: `select_for_update()` в коде остаётся
  ради переносимости, но на защиту от гонки не рассчитывать.
- Тестовая база — файл `backend/test_db.sqlite3` через `TEST.NAME`; in-memory
  база с shared cache не держит блокировки между потоками.
- Схема — только через миграции.
- Индексы: `loans(copy_id, start_date, due_date)`, `loans(reader_id)`,
  `reservations(book_id, status, created_at)`, `activity_log(created_at)`.
- Отчёты — агрегация в БД (`annotate`, `Count`, `Sum`, `Coalesce`). Расчёт в
  Python-цикле по всем записям запрещён.
- Период в отчётах — в `ON` у `LEFT JOIN`, иначе книги без выдач исчезнут.
- Только параметризованные запросы, без склейки SQL.
- Даты — `DATE` для периода брони, `DATETIME` для `hold_until`; таймзона
  `Europe/Moscow`.

## 5. API

- Префикс `/api/`, JSON, snake_case.
- Ошибки: `{"detail": "...", "code": "..."}`.
- Коды: 400 валидация, 401 токен, 403 роль, 404 нет объекта, 409 конфликт.
- Списки — с серверной пагинацией, поиском и фильтрами.
- Даты — ISO 8601 (`YYYY-MM-DD` для периода).
- Публичные `register`/`login`/`refresh` не разбирают `Authorization`:
  `authentication_classes = []`, иначе старый access ломает вход.
- CSV: UTF-8 с BOM; значения, начинающиеся с `=`, `+`, `-`, `@`, `\t`, `\r`,
  экранируются, чтобы Excel не выполнил формулу.

## 6. Frontend

- Функциональные компоненты и хуки, без классов.
- HTTP — только через `api/client.js`, состояние авторизации — в `AuthContext`.
- Один интерцептор: 401 → один `/refresh` → повтор запроса; неудача → выход.
- На каждом экране: загрузка, пустой список, ошибка, повтор.
- Формы: клиентская валидация + серверные ошибки по полям.
- Стили простые, без тяжёлых UI-библиотек.

## 7. Тесты

- `TestCase` для логики, `TransactionTestCase` + потоки для конкурентности.
- Минимум 15, цель — 23 из `docs/SPEC.md`.
- Обязательные группы: auth/JWT, права и чужие объекты, статусы, пересечения и
  смежные интервалы, 10 параллельных запросов, очередь и удержание, отчёт, CSV.
- Тест 10 потоков идёт на файловой тестовой базе (`TEST.NAME`) и требует
  `transaction_mode="IMMEDIATE"`; при `database table is locked` сначала
  проверить эти две настройки, а не ослаблять тест.
- Перед коммитом `python manage.py test --noinput` — всё зелёное.
- Падающий тест коммитится отдельно от исправления.
- Тест не подгоняется под реализацию: проверяем поведение.
- Вывод прогона не заворачивать в `Select-Object`/`Out-String`: пайп буферизует
  результат и выглядит как зависание. Запускать `manage.py test` напрямую или
  перенаправлять вывод в файл.

## 8. Документация и процесс

- Каждая значимая задача — запись в `docs/AI_LOG.md`: задача, ID сессии,
  результат, что исправлено.
- После каждой сессии: `opencode export <sessionID> > docs/prompts/<дата>-<тема>.json`.
- `docs/prompts/` не редактируется и не чистится; неудачные промпты — часть работы.
- Ошибки агента — в `AI_LOG.md`, повторяемые — правилом здесь.
- Аудит в `docs/AI_REVIEW.md`: находка → исправлено / отклонено и почему.
- Перед коммитом проверить дифф на секреты и отладочный код.

## 9. Контекст

- Одна задача за сессию, маленькими заходами.
- Не прикреплять `node_modules`, `venv`, `dist`, `*.sqlite3`, логи,
  `docs/prompts/*.json`.
- Новая сессия (`/new`), если контекст разросся или сменилась тема.
- Сначала прочитать `docs/SPEC.md` и `docs/PLAN.md`, потом менять код.
- Точечные изменения вместо перезаписи файла.

## 10. Запрещено

- Менять стек, схему или требования без записи в SPEC.
- Добавлять зависимости без необходимости.
- Оставлять `print`, `TODO`, `console.log`, закомментированный код.
- Хардкодить пароли, ключи, URL и тестовые данные в рабочем коде.
- Трогать `.env`, применённые миграции, файлы вне задачи.
- Отключать или удалять тесты, чтобы «стало зелёным».
- Обходить проверку прав, потому что «фронтенд скрывает кнопку».
