## 2. Проверено, нарушений не найдено

- **Права доступа.** Роль берётся из проверенного JWT. `user_id` не читается из
  тела или URL. Читатель видит только свои брони и заявки (`scoped_loans`,
  фильтр по `reader`), чужой объект отдаёт `404`. Отчёты, CSV и журнал — только
  `admin`; создание библиотекаря не принимает роль из тела.
- **JWT.** Access 15 минут, refresh 7 дней, тип токена проверяется SimpleJWT.
  Logout отправляет refresh в blacklist. Публичные эндпоинты не требуют токен.
  В payload нет лишних данных: только `user_id`, сроки и тип.
- **SQL-инъекции.** Прикладной код использует только ORM (`filter`,
  `annotate`, `FilteredRelation`, `Q`). Сырой SQL есть только в тестах
  (`reports/tests.py`) и параметризован через `%s`. Склейки SQL строками нет.
- **Валидация дат.** `resolve_period`: начало не в прошлом, `due_date > start_date`,
  срок не больше 30 дней. Фильтры периода проверяют `date_from <= date_to`
  (броней, отчётов, журнала). Даты периода — `DATE`, `hold_until` — `DATETIME`,
  сравнения через aware `datetime` в `Europe/Moscow`.
- **Двойная выдача.** Создание брони всегда в `transaction.atomic()`, а транзакция
  в SQLite стартует как `BEGIN IMMEDIATE` (`transaction_mode` в настройках):
  блокировка записи берётся до чтения, поэтому проверка пересечений и `INSERT`
  идут последовательно и не расходятся между потоками. Учитываются брони
  `created`/`active` и чужие действующие удержания. Конфликт — `409 copy_taken`,
  нет экземпляров — `409 no_copies`.
- **Очередь и удержание.** Порядок FIFO `ORDER BY created_at, id`; одна активная
  заявка читателя на книгу (`409 already_queued`); возврат и передача удержания —
  одна транзакция с блокировкой записи; `hold_until = +48 часов`; `ready →
  fulfilled` при создании брони; просроченное удержание становится `expired` без
  фоновых задач — при проверке доступности и при следующем возврате.
- **Секреты.** `DJANGO_SECRET_KEY` обязателен и читается только из `backend/.env`;
  `DEBUG` по умолчанию `False`; `ALLOWED_HOSTS` и `CORS_ALLOWED_ORIGINS` — из
  окружения. Пароля базы нет: SQLite — локальный файл. В рабочем дереве нет
  ключей и паролей вне `.env`; `.gitignore` исключает `.env`, `.env.*`, `venv`,
  `node_modules`, `dist`, `*.sqlite3`, логи.
  В `backend/.env.example` и `frontend/.env.example` только заглушки.
- **Смена статусов.** Матрица только в `loans/statuses.py`; недопустимый переход
  — `409 bad_transition`; смена статуса, `LoanStatusHistory` и `ActivityLog`
  пишутся в одной транзакции.
- **Отчёты.** Агрегация в БД, период в `ON` у `LEFT JOIN` через `FilteredRelation`,
  поэтому книги без выдач остаются в результате. CSV в UTF-8 с BOM.
- **Frontend.** HTTP только через `api/client.js`; один refresh-интерцептор;
  на экранах есть загрузка, пустое состояние, ошибка и повтор. Скрытие кнопки не
  подменяет серверную проверку прав.

## 3. Отклонённые находки и принятые риски

| # | Находка | Решение | Причина |
|---|---------|---------|---------|
| 1 | Проверка истории Git и секретов в коммитах | Отклонено | Проект не является git-репозиторием (`git status` → `not a git repository`). Проверено рабочее дерево и `.gitignore`; историю коммитов проверить нельзя. |
| 2 | `get_client_ip` доверяет `X-Forwarded-For` | Принято как риск | IP в журнале носит справочный характер, ни одно решение доступа от него не зависит. Заголовок подделывается клиентом; корректная проверка возможна только за доверенным reverse proxy. Ошибки записи журнала перехватываются и не ломают запрос. |
| 3 | Access-токен действует до 15 минут после выхода | Принято как риск | JWT stateless: отзыв access требует проверки БД на каждом запросе. Срок короткий, refresh при выходе попадает в blacklist. Для учебного проекта это осознанный компромисс. |
| 4 | Удержание истекает не по таймеру, а при проверке | Отклонено | Прямо предусмотрено `AGENTS.md` 3.2 и SPEC: фоновые задачи не используются. Истечение проверено тестами доступности и возврата. |
| 5 | Нет ограничения частоты попыток входа | Отклонено | Не входит в SPEC и в объём учебного проекта; для production нужен rate limit на уровне reverse proxy или Django-пакета. |
| 6 | Тест конкурентности не выполняется на SQLite | Закрыто | По решению владельца проекта база переведена на SQLite. Тест 10 потоков проходит: файловая тестовая база (`TEST.NAME`) плюс `transaction_mode="IMMEDIATE"` — транзакция берёт блокировку записи до чтения. Проверено: 1×`201`, 9×`409 copy_taken`. |
| 7 | CSRF-защита для API | Отклонено | Аутентификация только Bearer-токеном, сессионные cookie не используются; CSRF неприменим. |
| 8 | Пароль MySQL из `backend/.env` попал в экспорты сессий в `prompts/` | Закрыто | Пароль больше нигде не используется: проект переведён на SQLite, сервер MySQL не нужен. Историю промптов не редактировали — по правилу `AGENTS.md` она неизменяема. В `prompts/PROMPTS_LOG.md` аргументы команд не выводятся, поэтому пароль туда не продублирован. |

## 5. Остающиеся ограничения

- Нет git-репозитория: историю изменений и коммиты проверить невозможно.
- Нет rate limiting для входа и сброса пароля: вне SPEC.
- IP в журнале можно подделать заголовком `X-Forwarded-For` без доверенного прокси.
- Access-токен не отзывается досрочно, живёт до 15 минут.
- В отчётах «загрузка» считается как `copies_used / copies_total * 100` по
  задействованным экземплярам; другой методики SPEC не задаёт.
- SQLite: одна запись в момент времени и отсутствие блокировок строк.
  `select_for_update()` оставлен в коде ради переносимости, но на SQLite ничего
  не блокирует; защиту даёт `transaction_mode="IMMEDIATE"`. При росте нагрузки
  понадобится серверная СУБД.
- Файл `backend/db.sqlite3` лежит в синхронизируемой папке OneDrive: параллельный
  запуск тестов и сервера может дать `database is locked`. Это ограничение
  окружения, а не кода.

## 6. Изменение стека по решению владельца

16.11.2026 база данных переведена с MySQL 8 на SQLite 3: владельцу проекта нужна
база внутри проекта, без отдельного сервера.

Что изменено:

- `config/settings.py`: `django.db.backends.sqlite3`, файл `backend/db.sqlite3`,
  `transaction_mode="IMMEDIATE"`, `timeout=20`;
- тестовая база — файл `backend/test_db.sqlite3` (`TEST.NAME`): на in-memory базе
  с shared cache потоки падают с `database table is locked`;
- `requirements.txt`: убран `mysqlclient`;
- `.env.example`: убраны `DB_*`; `.gitignore`: добавлен `test_db.sqlite3`;
- `scripts/concurrent_booking.py`: снят запрет на не-MySQL;
- `docs/SPEC.md`, `AGENTS.md`, `docs/PLAN.md`, `README.md`: стек, инвариант
  защиты от двойной выдачи, тесты и ограничения переписаны под SQLite.

Что сохранено: тест на 10 параллельных запросов не удалён и не ослаблен — он
проходит на SQLite и по-прежнему проверяет, что создаётся ровно одна бронь.
Цена решения: блокировок строк нет, конкурентная запись сериализуется целиком.
